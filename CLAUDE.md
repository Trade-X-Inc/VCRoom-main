## 0a. CC does not design

**CC extracts and implements. CC does not design.**

Every internal and external page follows the founder's Figma file EXACTLY — same layout, same component placement, same spacing, same structure — extracted via the Figma connector (`get_design_context`) or from provided frame code. Never approximated. Never "inspired by." Never rebuilt from a borrowed pattern, a remembered shape, or a judgment call about what would read better.

**If a Figma frame doesn't exist for a screen, STOP and ask before inventing a layout.** Do not fill the gap with a design decision of your own, however small — report the gap and wait.

**Content and workflow logic are NOT covered by this rule.** Copy, data bindings, business logic, and workflow sequencing come from the founder and from the real product's actual behaviour, separately from the Figma extraction — per the founder's explicit instruction, Figma for internal-app screens can carry the wrong workflow or invented content (see the "CapitalClose" template residue found 30 Aug 2026: wrong brand name, "Execute Settlement," "Liquidity," a "Worklist"/"Waiting on You" feature set that doesn't exist in the product). Only visual layout, structure, and design system are extracted verbatim. Never port a Figma frame's copy, feature set, or workflow assumptions — those are corrected or replaced with the real thing, same as the public-site content-correction pattern already in use (§2 below refers to the equivalent public-site rule).

**Found the hard way, 30 Aug 2026:** a first pass at `app.deal-rooms.$id.overview.tsx` was rebuilt as a "bento-grid layout... borrowing the stat-tile and grid-arrangement pattern from a Figma design reference" — narrated as design-influenced, not copied. This was reverted (commit `6762891`, reverted `eb85d58`) specifically because "borrowed pattern" is not the standard. The correct process is: find the actual matching Figma frame, extract its exact layout via `get_design_context`, and implement that — not a layout CC judged to be inspired by it. Do not repeat this. A verification pass that only checks "does this look plausible against the general design language" is not sufficient — it must check against the specific frame.

## 1. The one rule

**Audit before you build. Report before you merge.**

Every phase begins with a read-only step 0 that produces a written report and stops. No code, no migrations, no drops until that report is reviewed and approved.

This rule exists because it has repeatedly found things that would not otherwise have been found: a live authorisation bypass, a template-literal bug that survived a clean build, a security test that passed while the vulnerability was open.

## 4. Confirm-first rule

Claude Code never performs these without explicit approval in the same session:

- Dropping or altering a database table
- Deleting a file that is not clearly dead
- Modifying anything under `src/lib/auth.tsx` or `src/lib/supabase.ts`
- Writing to production data, including "temporary" probe rows
- Changing anything in Cloudflare, Supabase dashboard, or DNS
- Merging or pushing

If a test requires a write to production, stop and ask first. Disclosing it afterwards is not the same thing.

**Deploying a new Supabase Edge Function is additionally gated by §19d.1**, which carries the same blocking weight as this section: no new edge function may be deployed without deriving caller identity through the shared identity-derivation helper. `verify_jwt: true` alone does not satisfy it.

## 4a. One agent per folder

**Only one agent — Claude Code or GitHub Copilot — may write to a given folder at a time.** Before switching which agent is working in a folder, confirm the other agent's process or session is actually closed, and confirm `git status` is clean for that folder before starting.

**Commit after every discrete step, no exceptions.** This is what makes a bad edit revertable in seconds instead of costing a full recovery pass.

This rule exists because of a real incident (24 Aug 2026, `lengdon-public-site/`): a headless Copilot process, still attached to the same VS Code workspace, silently rewrote an entire file underneath an in-progress Claude Code audit — collapsing 29,595 bytes to 13,688, destroying nearly all page-specific content while still passing a syntax check — and the damage was undetected until a second full audit compared output against the first audit's own transcript. The file had never been committed, so recovery depended entirely on reconstructing content from a prior report rather than `git diff`. Committing after every step and confirming exclusive write access before starting are what turn an incident like this into a one-line revert instead of a forensic recovery.

## 5. Build discipline

- Branch per phase. Commit per numbered step.
- Merge `--no-ff`, never squash.
- **Never run `npm run deploy`.** Push only — Git integration deploys.
- Verify the committed tree equals the tested tree before merge. Working tree clean, `git status --porcelain` empty.
- Report `tsc` error count and gzip bundle size before and after every branch.
- **After any change touching secrets, build configuration, or a key rotation: grep the BUILT ARTIFACT for the secret's format, not the source.** Client, server and worker output, plus the deployed bundle where a deploy has happened (a local build and a CI build can differ in env). Source-level greps and removed call sites prove nothing about what the bundler emits — see §19e, where a correct source-level remediation left a live API key in the production bundle for eleven weeks.
- A security gap found mid-phase is never "out of scope". Stop and report it.

## 6. Verification standards

**Claims are not evidence.** A report saying "verified" without raw output is not a report.

- Paste raw `curl` output, raw query results, raw status codes. Not summaries.
- Adversarial tests run as a real authenticated account with genuinely no access — not as a privileged role.
- When testing whether a protection holds, attempt the actual attack. Reading the code is not a test.
- **Shadow every table a function touches, not just the first.** A partial test produces a false pass. This exact mistake once produced a clean bill of health on a live vulnerability.
- Verify worker-injected code against the **pre-minified** assembled string. Reading minified output has produced a wrong diagnosis before.

## 7. Known defect patterns — do not reintroduce

These were found the hard way. Each cost hours.

### 7.1 Authorisation

- **Never trust an identity parameter.** A `user_id` in a request body is spoofable. Derive identity from the session, always. Delete the parameter rather than validating it.
- **Service-role code bypasses RLS entirely.** There is no database backstop. Authorisation must be complete in the code.
- **"A row exists matching these IDs" is not an authorisation check.** It must be "the caller *is* the party in that row."
- **RLS helper functions that query their own protected table cause infinite recursion.** Use direct subqueries or a `SECURITY DEFINER` helper.
- **`auth.email()` outperforms `(SELECT email FROM auth.users WHERE id = auth.uid())`** — the latter silently fails for the authenticated role.
- **`requireUser()` authenticates the token, not the possessor.** A stolen valid token passes every check in this codebase, everywhere. This is an accepted boundary, not a gap in any single function — do not re-litigate it per-function.
- **When auditing any Supabase Edge Function's auth, test whether the public anon key (present in every frontend bundle) is itself accepted as a valid JWT.** `verify_jwt: true` alone does not exclude it — the anon key is a real, platform-signed JWT, so a JWT-format check passes it; only a claims check (e.g. rejecting a token with no `sub`) excludes it. Test explicitly, do not assume a JWT check excludes unauthenticated callers.
- **A caller-side ownership check is not function-enforced authorization.** If the only thing standing between a request and the data is that *the caller* verified ownership before calling, then any other caller reaching the same endpoint bypasses it entirely. **OPEN ITEM, `daily-desk-cron` (11 Aug 2026):** `founder_id`/`startup_id` arrive as query params with no in-function derivation; the sole mitigation is that `seedFounderPlaybook` runs `requireUser` + a `founder_id` ownership match before invoking with the service-role key. `verify_jwt` was flipped `true` the same day, which closes the anonymous path but **not** this gap — any authenticated principal can still target another founder's ids. Full fix (`requireUser` + ownership check inside the function) is scoped for this function's rebuild. See §19d.
- **Disabling a trigger (cron, schedule, event) is not equivalent to disabling what it triggers.** A function remains invokable by anyone with the URL regardless of whether anything currently calls it automatically. Verify the function's own auth/exposure separately from confirming its triggers are off. Found live 11 Aug 2026: `verify-investor` and `match-investors` had their cron jobs unscheduled on 3 Aug 2026 and CLAUDE.md §19 was written as though this closed the incident — but both functions remained the full original implementations, `verify_jwt: false`, no in-code auth, publicly invokable by anyone with the URL, for eight more days. See §19's correction and §19b.

### 7.2 SECURITY DEFINER functions

- `SET search_path TO 'public'` is **not** safe. `pg_temp` is searched implicitly first. Use `SET search_path = public, pg_temp` (pg_temp last) or `SET search_path = ''` with fully-qualified names.
- Functions owned by `postgres` have `BYPASSRLS`. RLS is not a backstop inside them.
- **Inside a `SECURITY DEFINER` function, `current_user` and `session_user` both report the function's OWNER, never the caller.** Only `current_setting('role', true)` reflects the role PostgREST switched to for the request. Probed directly to confirm (9 Aug 2026): with `set local role authenticated`, a `SECURITY DEFINER` function observes `current_user=postgres`, `session_user=postgres`, `current_setting('role')=authenticated`. A trigger guard that gated itself on `current_user <> 'authenticated'` therefore disabled itself for **every** caller including the one it was written to constrain — shipped and caught within minutes by re-running the adversarial probe that had passed before, not by reading the function. Never use `current_user` for a caller-role check inside a `SECURITY DEFINER` function.
- **A `BEFORE UPDATE` trigger written to column-scope one RLS policy will also fire for service-role and `SECURITY DEFINER` writers, which that policy never governed.** Same 9 Aug 2026 incident: a guard whose bypass condition was `auth.uid()`-derived (`is_startup_founder`) rejected all nine service-role `deal_rooms` writers and `finalize_deal_close()`, blocking stage advance, term-sheet response, pass-deal and deal closing in production. A trigger's scope is every writer of the table; an RLS policy's scope is one role. When adding a trigger to constrain a policy, gate it explicitly on the role that policy admits, and test the privileged paths — not only the path being constrained.
- **New `SECURITY DEFINER` functions inherit `EXECUTE TO PUBLIC` by default.** Every `pack_api` function requires an explicit `REVOKE EXECUTE FROM PUBLIC` and `GRANT` to `service_role`, verified live with an `anon` call, not assumed because every other function in the schema follows the convention. Convention is precisely what failed here — six `room_get_*` functions (9 Aug 2026, step 2c) were created without the revoke, and the omission was invisible until tested: `set local role anon` plus a real user's uuid as `p_uid` returned that user's actual room data (`p_uid` is caller-supplied, never derived from `auth.uid()` — see the §7.1 identity-parameter rule — so the only thing standing between an anonymous caller and real data was the grant). Caught by the adversarial matrix itself, fixed the same session, re-verified live that `authenticated` now gets a genuine `permission denied for function` error. Check every new `pack_api` function's grants against `information_schema.role_routine_grants` before considering it done, not after something else surfaces the gap.
- A function that is RPC-reachable, takes a caller-supplied ID, and returns data is a data-exposure surface regardless of `search_path`. RLS helpers belong in an unexposed schema.
- Revoking `EXECUTE` from `authenticated` does not work for RLS helpers — policy expressions run as the querying user.
- `REVOKE TEMPORARY ... FROM authenticated` is a no-op. `TEMPORARY` is granted to `PUBLIC`.

### 7.3 Cloudflare and the worker

- `_headers` and `_redirects` do **not** apply to SSR-routed responses. Headers and redirects must be injected in the worker via `patch-wrangler.mjs`.
- `patch-wrangler.mjs` and `public/_headers` must stay in sync. Editing one without the other silently diverges production.
- **Regex inside `patch-wrangler.mjs` template literals is consumed at Node build time.** A literal `\d` or `\/` does not survive. Use `String.fromCharCode(92)` construction and verify against the pre-minified string.
- `React.lazy` does not reduce the Pages `_worker.js` — esbuild `--outfile` inlines dynamic imports. Only `--external` affects the worker. Client-side splitting still helps the client bundle.
- Edge-cached HTML referencing hashed asset filenames can break after a deploy. Keep edge TTL short on cached routes.

### 7.4 Application

- **One Supabase auth listener only.** Multiple listeners cause 5-second localStorage lock timeouts. Two currently exist (`lib/auth.tsx`, `lib/auth-store.ts`), each individually guarded — resolve during the rebuild.
- **Soft-delete files** by setting the parent reference to null. Never hard-delete from storage. *(See §11.2 — this conflicts with the erasure requirement and must be reconciled.)*
- **Errors must be checked.** A destructured `error` that is never referenced produces silent failure and false success in the interface. This class shipped to production more than once.
- **A caught failure that renders a plausible success state is worse than an uncaught one.** Gateway/action call failures must surface as errors, never as empty-but-valid-looking UI. An empty state must mean "no data exists," never "the request failed." Found live 13 Aug 2026 (§20.11): three `callAction` call sites (the founder deal-room list, `useRaiseProgress`, `useDealFlowProgress`) caught every gateway failure — including a total transport failure, not just the expected zero-result case — and degraded to `[]`. This is precisely what hid the §20.11 server-fn split outage: for eleven days, founders with real deal rooms saw "No deal rooms yet." with no error, no toast, nothing distinguishing it from a genuinely empty account. Reverted the same day the outage was fixed — the query now lets a real failure propagate into React Query's own error state, and the UI renders an explicit "could not load" message with a retry action instead of a fake empty list. The narrower pattern (mapping a *specific* named error like `"forbidden"` to `null`, re-throwing everything else — used correctly in `qa.tsx`, `DealTermsCard.tsx`, `DDWorkstation.tsx`) is not this defect; the distinguishing question is whether *every* failure is swallowed or only one specifically-identified, expected one.
- **Checking the error is not sufficient — PostgREST returns no error for a 0-row `UPDATE`.** An `UPDATE` rejected by RLS (no row matched the `USING` clause) is indistinguishable at the client from an `UPDATE` that legitimately matched zero rows for an unrelated reason: `if (error) throw error` passes in both cases. Found live on `deal_rooms` during the deal-room-core step-0 audit (5 Aug 2026): `app.investor.analysis.tsx`'s `handleSaveMemo` showed `toast.success("Memo saved to deal room")` on every investor click while the row genuinely never changed, because no RLS write policy existed for investors on that table at all. Verified live in a rolled-back transaction: investor `UPDATE` affected 0 rows, the identical `UPDATE` as the room's founder affected 1. Every gateway write function must return an affected-row count, and the client must treat 0 as failure, not silently render the success path.
- **A single RLS `UPDATE` policy grants the whole row, never specific columns.** There is no native column-scoped `UPDATE` policy in Postgres — `USING`/`WITH CHECK` gate which rows are reachable, not which columns of a reachable row may change. Found live while fixing the defect above: a policy written to let an investor update only `investor_memo`/`memo_generated_at` on `deal_rooms` also silently granted them `workflow_stage`, `funding_ask`, and every other column on the same row, because the policy had no column predicate — caught before merge by testing a non-memo column, not by reading the policy. The actual column restriction requires a `BEFORE UPDATE` trigger comparing `NEW`/`OLD` on every column outside the intended allow-list and raising if any differ (see `pack_api.enforce_deal_rooms_investor_memo_only()`, migration `20260809000000`). Any future column-scoped write grant needs the same two-part shape — policy for row reachability, trigger for column scope — not the policy alone.
- **A client-computed jsonb array append (`[...existing, newValue]`) from a stale read is silent DATA LOSS, not a "conflict."** Same class as the 0-row silent-write finding above — a real failure with no error and no visible symptom. `DDWorkstation.tsx`'s `product_images` write read the array, appended a URL client-side, and wrote the whole array back with no version check. Two founders (or one founder in two tabs) uploading images within the same window: the second write overwrites the first's array wholesale, so the first upload's reference vanishes — no error, no toast, nothing to indicate it ever happened. This was a pre-existing live defect, found and fixed during deal-room-core's §20.4 error-semantics pass (10 Aug 2026), not a byproduct of adding concurrency handling — the concurrency design (`updated_at` compare-and-swap, `pack_api.room_append_product_image`) is what closes it, but the defect itself predates that work. Verified live: forced the exact two-writer race (image-A appended, image-B attempted against the pre-A `updated_at`) — before the fix this would have left only image-B; after, B's write is rejected as `conflict` and image-A survives untouched. Any future array-append write against a wide row needs a compare-and-swap or a dedicated append RPC — never a client-side read-modify-write on a shared array column.
- `investor_profiles.id` (profile PK) is **not** `investor_profiles.user_id` (= `auth.uid()`). Never conflate.
- Do not hand-roll workflow transitions across an enum. The prior codebase ended with two conflicting stage vocabularies and a live constraint violation.
- **A table can carry two independently-written "stage" columns that look interchangeable but are not.** `deal_rooms.status` and `deal_rooms.workflow_stage` both read as lifecycle state, but only `status` is real: it is guarded by an immutable-once-closed trigger (`enforce_deal_room_close_guard`) and can only reach `'closed'` through `finalize_deal_close()`, which requires both parties' recorded mutual confirmation (`deal_room_close.investor_confirmed`/`founder_confirmed`). `workflow_stage` is written directly by a separate, unguarded, single-party-approvable path (`useStageTransition.ts`'s `approveTransition`) with no mutual-confirmation requirement and no trigger. A step-0 audit's first read of a room with `workflow_stage='closed'`, `status='active'` concluded `status` was stale and wrong; deeper tracing (the trigger, the RPC, `deal_room_close`'s empty confirmation row on that exact room) showed `status` was correct and `workflow_stage` was the stale/separate signal — the opposite conclusion. **Before trusting which of two same-shaped columns is authoritative, trace every trigger and RPC that writes either one, not just which UI reads which.**
- **`status` and `workflow_stage` are NOT two vocabularies for the same concept — do not reconcile them by making one read the other.** `status` is the trigger-protected, mutually-confirmed, authoritative close state with 18 dependent RLS policies (via `rls_private.dr_is_open`). `workflow_stage` is an unguarded progress indicator. They answer different questions and a "fix" that points one at the other — in either direction — breaks the close mechanism or the progress display. This was proposed once (8 Aug 2026), verified wrong before it was applied, and is recorded here so it is not re-proposed. Any future change to either column starts from the premise that both are legitimate and separately owned; the open question is naming and constraint, not unification.
- **AI-provider fallback conditions must fail closed on absent configuration, never fail open.** A condition like `|| !API_KEY` silently routes to an unapproved provider on a merely missing env var — no deliberate flag required. Every fallback must be explicit opt-in, never a byproduct of missing config. Found live 11 Aug 2026: `review-document`'s `getAIConfig()` read `const useOpenRouter = FORCE_OPENROUTER || !OPENAI_KEY` — the founder-financial-document review path would have silently sent content to `deepseek/deepseek-r1:free` (an unapproved second provider, §10) the moment `OPENAI_API_KEY` was unset, with no flag ever flipped. Fixed to return `null` (fail closed, `503`) when the key is absent; see §19b.
  > **CORRECTION, 11 Aug 2026 — this entry originally described a single instance. It is a RECURRING pattern, not a one-off.** The live-function inventory later the same day found the identical condition in **`extract-pitch-deck`** (`FORCE_OPENROUTER || !OPENAI_KEY` → `deepseek/deepseek-chat`), where the content at risk was an entire uploaded pitch deck. Fixed identically (deployed v13, fail closed, `503`; deployed body verified to contain zero OpenRouter references). Two instances of the same copy-pasted fallback in two separate functions means the next new AI-calling function is likely to carry it too — **check this specific condition on every function that calls a model, do not assume it was a single author's mistake.** Both known instances are now fixed; `ai-router` was already single-provider.
- **A comment acknowledging content is fabricated or a placeholder does NOT make it safe to ship — it demonstrates the author knew and shipped anyway.** Treat an admitted-placeholder value the same as an unlabeled one: it does not go live. The acknowledgement is evidence of the defect, never a mitigation of it, and it is strictly worse than an unlabelled invention in one respect — it proves the decision was made consciously rather than by oversight. A reviewer encountering `// placeholder — replace with real data later` next to a user-facing value must treat that comment as a blocker, not as reassurance that someone has it in hand. Found live 11 Aug 2026 in `daily-nudge-cron` (see the entry below for that specific instance).
- **A "placeholder" statistic in outbound copy is a shipped fabrication, not a TODO.** Foundation Document §3.8 prohibits invented signals; a fabricated multiplier does not become permissible because a comment next to it admits it is fake and promises to replace it later. **Two confirmed instances, both in live outbound email, both with the author's own acknowledgement adjacent:** (1) `send-onboarding-emails` — *"Profiles above 80% get 3x more investor views on average"* (§19b); (2) `daily-nudge-cron` — *"Investors who are invited to a deal room within a week of approval are 3× more likely to submit a decision"*, directly beneath the source comment *"Placeholder statistic: update with real platform data once sufficient sample size is reached."* Both functions are now stubbed, so neither can send again — but the pattern is what matters: the intent to fix later is precisely what let a known-false claim ship to real users. **A statistic with no computed source does not go into user-facing copy at all — not behind a TODO, not as a placeholder, not "until we have real data."** Write the sentence without the number, or omit the sentence.
- **A fabricated value styled to look like cryptographic proof is a MORE dangerous fabrication than a plain invented statistic — never render one over data that isn't real, including in a clearly-labelled mock.** A hash, a signature, a fingerprint, a sealed-record digest, a check-digit-bearing identifier: the visual form itself is what manufactures trust. A reader who would rightly question "3x more investor views" will not question `0x8F9B2A…D94E`, because the shape of the thing asserts that something was computed and can be verified. That assertion is the fabrication, and a "design preview" label does not neutralise it — the label explains the page, while the artifact keeps making its own claim, and screenshots outlive their captions. This is strictly worse than an invented number, which at least presents as a number. **Where a real value cannot be computed, omit the element entirely rather than filling it.** Established 31 Aug 2026 building the advisor record-export preview (§20.15): Figma frame `35:3313` carried a "TERMINAL HASH `0x9f8c3b4a…`" tile over invented deal data, and it was dropped rather than rendered, on the same reasoning that dropped the frame's "Export PDF"/"Share Record" buttons — §12 already records "sealed export" as one of four differentiator claims found FALSE of the live product and removed from public copy, so rendering a verifiable-looking artifact of that capability would have re-introduced the claim inside the app. Note the asymmetry with reference numbers on that same screen, which WERE rendered: those carry a real, spec'd, check-digit-verified format (§8.4) computed by the actual implementation, so the form makes a claim the value can honour. A hash over fictional entries can honour nothing.

## 8. Architecture rules for the rebuild

> **CURRENT STATE (verified 2 Aug 2026):** everything in §8 below is prospective — none of it has been built yet. There is no action-layer directory, no gateway module, no naming convention indicating a chokepoint. Actual measured shape of the codebase today: 65 files under `src/routes`/`src/components` call `supabase.from()` directly from the client (RLS-governed, not gateway-routed); 50 files in `src/lib` define independent `createServerFn` handlers, each authorising on its own; 25 of those use the shared `requireUser()` identity helper (added by the R43 branch, merged to `main`) but there is no single entry point they all pass through. This is precisely the "scattered across a hundred policies and forty functions with no chokepoint" failure mode §8.1 describes below — meaning §8.1–§8.4 describe the fix, not the present. Treat every rule below as Phase-1-not-started design intent until this note is removed.

### 8.1 The action layer

**The client never queries the database directly.** Every read and write passes through a server action that derives identity from the session and enforces authorisation in one place.

RLS remains as a second layer but is no longer the primary boundary. Nearly every security incident in this codebase followed from authorisation scattered across a hundred policies and forty functions with no chokepoint. One gateway is auditable by a person; a hundred policies are not.

### 8.2 Actions are tools

Every action is defined once, at an interface-independent layer, with a typed contract, complete authorisation, and its own audit entry. The web interface and the agent interface are both consumers.

**No action may exist only as a UI event handler.** Retrofitting this later means rewriting the entire action layer.

Tool classes:

| Class | Agent may | Examples |
|---|---|---|
| **Read** | Execute freely within the principal's permissions | Read pack, list requests, get status |
| **Prepare** | Produce a draft a human must commit | Draft a request batch, draft an answer |
| **Commit** | **Never** | Accept a term, sign, close, decline, release a document |

No agent executes a Commit-class action under any circumstance, including explicit user instruction.

### 8.3 The record

> **CURRENT STATE (updated 4 Aug 2026):** first implementation built and verified in the **isolated `pack_v1` schema** (Phase 1 sub-milestone A, migration `supabase/migrations/pack_v1/20260804000000_pack_v1_foundation.sql`, commit `cfd20f5`). NOT in `public`, NOT promoted, 0 real entries — `pack_v1` is a discardable design-proving namespace (Supabase branching is Pro-only and unavailable on this project; schema isolation is the approved substitute). `record_entry` is one append-only hash-chain per org; `append_record()` is the sole writer; UPDATE/DELETE blocked by trigger (defense-in-depth — a superuser can `DISABLE TRIGGER`, so the hash chain itself, not the trigger, is the real tamper-evidence). Verified live: genesis + links, per-org independence, all three actor types, immutability, and independent hash recomputation. Still prospective in `public` until cutover.

Append-only, hash-chained. Each entry carries its predecessor's hash. Entries record actor identity, actor type (human / agent / system), timestamp, object reference, action.

Cannot be retrofitted onto existing history. Build it from the first write.

**`entry_hash = sha256(prev_hash || canonical_json(payload))`. The canonicalisation is spec'd, versioned, and authoritative in [`supabase/migrations/pack_v1/CANONICAL_JSON_SPEC.md`](supabase/migrations/pack_v1/CANONICAL_JSON_SPEC.md) — the Postgres function is the reference implementation, that document is what any second implementation (export tooling, client verifier, auditor) is checked against.** Key traps it records, found by probing actual output, not intent: number trailing-zeros are PRESERVED (`1.50` ≠ `1.5` — this is deliberately NOT RFC 8785/JCS, which would normalise them), object keys are recursively code-point-sorted while array order is preserved, and numbers must be carried as arbitrary-precision decimals never floats. Changing canonicalisation once real entries exist is a breaking, versioned change with product-owner sign-off — never a silent edit.

### 8.4 Reference numbering

> **CURRENT STATE (verified 2 Aug 2026):** does not exist in any form. Zero matches anywhere in the codebase or migration history for `{ORG}-{TYP}-{YYYY}-{SEQ}-{CD}`-style formatting, ISO 7064 MOD 97-10, or any `reference_number`/`ref_no` column. Entirely prospective.

Format: `{ORG}-{TYP}-{YYYY}-{SEQ}-{CD}` — `ATLS01-ROM-2026-000042-31`

Sequences are gapless per organisation, per type, per year. Check digit is ISO 7064 MOD 97-10. **An observed gap is a records incident to be investigated, never silently corrected.**

### 8.5 Never build

- PDF renderer, e-signature stack, workflow state machine — use libraries or vendors
- A platform fork of any kind. Libraries yes, platforms never. Our data model is the product.

## 10. AI usage

| Application | Rule |
|---|---|
| Extraction from documents | Proposes a value with citation to page and location. Human confirms; the confirmation is the warranty. |
| Completeness checking | Compares pack against schedule. Reports absence, never judgment. |
| Answer drafting | Drafts from existing pack data with citations. Human edits and sends. |
| Discrepancy detection | Flags a conflict. Does not resolve it. |
| Retrieval, search, translation | Permitted. Original always authoritative. |
| Scoring, ranking, recommendation, assessment | **Prohibited.** |
| Anything entering the record | **Prohibited.** Uncitable in a dispute. |
| Legal instrument generation | **Prohibited.** UPL exposure. |

**Injection containment:** uploaded documents are attacker-controlled text. Document content is delivered to a model as data, explicitly delimited, never as instruction. Content-derived values may populate fields awaiting human confirmation; they may never be passed as arguments to a Prepare or Commit tool without it. Read-class tools operating on document content cannot chain into another tool in the same turn.

**No provider-routing enforcement currently exists anywhere in the codebase.** `ai-router`'s `MODEL_MAP` routes every task type to OpenAI only (`gpt-4o-mini` or `gpt-4o`) — this is a single hardcoded provider, not an enforced routing policy; there is no code path that could route sensitive content elsewhere even accidentally, but there is also no mechanism that would catch it if one were added. No DPA is in place. OpenRouter key exists in secrets and is unwired. (Corrected 3 Aug 2026 — this line previously claimed enforcement existed; the `ai-router` audit found none. See §17.)

## 11. Security and compliance

### 11.1 Controls built from day one

- AES-256 at rest with managed key rotation
- TLS 1.3 enforced, legacy versions blocked
- Signed, short-lived URLs for every document. No persistent public URL.
- Tenant isolation at the action layer. No identifier in a request may widen access.
- **Mandatory MFA** — required, not a settings toggle
- Immutable hash-chained audit log recording actor, action, object, timestamp, source address
- Automated dependency scanning from the first commit
- Explicit recorded consent at onboarding per processing purpose

### 11.2 Erasure versus retention — unresolved

DIFC data protection law requires a genuine erasure capability for personal data. **This conflicts with the soft-delete rule in §7.4.**

Intended resolution: personal data erasable; transaction records retained and pseudonymised, with the party replaced by a permanent reference so the audit trail survives.

**This must be settled with counsel before the disclosure pack schema is finalised.** It is the one compliance question that changes the data model.

### 11.3 Certification

Build the controls now, delay the audit. SOC 2 Type II requires a 6–12 month observation window, so it begins around month 6, not when a customer asks.

A regulatory sandbox licence does **not** substitute for SOC 2. They are unrelated, and claiming otherwise damages credibility with anyone who knows the difference.

Claim nothing we do not hold. Publish what exists instead.

## 19d. The edge-function auth gap — systemic, inventoried and closed 11 Aug 2026

Four functions retired earlier in this session (`ai-router` §17, `generate-deal-brief`, `verify-investor`, `run-founder-coaching`) shared one defect exactly: `verify_jwt: false`, no identity derivation, spoofable caller-supplied identity. Four instances of an identical defect is a scaffolding gap, not four incidents — so a full inventory of every deployed function was run rather than continuing to fix them as they surfaced.

**Method:** enumerate all 20 deployed functions; re-verify every presumed stub live (all 9 returned a genuine `410` to a real platform-signed JWT — trusted from no record, since §19's record had already been found wrong once); read the **body** of each of the 11 live functions for its actual identity-derivation method rather than inferring from `verify_jwt` alone.

**The finding, stated plainly: one function out of eleven derived identity correctly — `ai-router`, the one already remediated in §17.** Every other function either had no identity concept at all or relied solely on the platform JWT gate. There is no shared auth helper: `ai-router`'s `resolveUid()` exists in exactly one file and was never extracted; `supabase/functions/_shared/` contains no auth module. Every function author made an independent decision and eight of eleven chose nothing.

**Six live functions matched the defect shape. Two were proven anonymously reachable, not merely assumed:**
- `send-nudges` — unauthenticated POST returned `200 {"nudges_sent":0,"rooms_checked":0,"rooms":[]}`, having executed a real `deal_rooms` query. It returned zero only because the probe used an id matching nothing; with an empty body it scans every active deal room and emails every investor with a stale one.
- `notify-access-request` — unauthenticated POST reached its own parameter validation (`400 "startup_id and investor_id are required"`).
- `daily-desk-cron` — unauthenticated POST with real query params returned `200 {"ok":true,...}`, executing the founder playbook path against a real founder.

**Disposition — five stubbed, one gated:**

| Function | Action | Verified |
|---|---|---|
| `profile-gate-nudge-cron` | cron unscheduled (jobid 6) + stub `410` | anon `401`, real JWT `410` |
| `notify-access-request` | stub `410` | anon `401`, real JWT `410` |
| `send-nudges` | stub `410` | anon `401`, real JWT `410` |
| `send-nudge-emails` | stub `410` | anon `401`, real JWT `410` |
| `daily-nudge-cron` | stub `410` (also closes a §3.8 fabrication) | anon `401`, real JWT `410` |
| `daily-desk-cron` | **`verify_jwt` false→true only** — has a live caller | anon `401`; **legitimate service-role call still `200`** |

**`profile-gate-nudge-cron` was the highest-severity item**: the only function both unauthenticated *and* actively cron-scheduled. Its own header comment argued no confirm-first gate applied because it is "scheduled infrastructure, not an AI-agent-callable tool" — true of the cron path, irrelevant to the open HTTP endpoint, and exactly the reasoning that kept it unexamined. Its cron had in fact never delivered (56/56 `pg_net` failures), but the endpoint was always open, which the cron's failure did nothing to mitigate.

**`daily-desk-cron` — batch pass RETIRED 11 Aug 2026 (deployed v10), fast path preserved.** After the `verify_jwt` flip closed anonymous access, the batch pass remained reachable by *any authenticated caller including anon-key holders*, running an unbounded OpenAI-spending pass over every user — proven when an audit probe triggered it (§19d.2). The parameterless branch now returns `410 {"error":"Gone","detail":"Batch pass retired..."}`; the single-founder `?founder_id=&startup_id=` path is untouched. **No admin-secret gate was added, deliberately** — same reasoning as deleting `triggerDeskCron`. All four branches verified live post-deploy, not inferred: batch + anon-key `410`, batch + service-role key `410` (the strongest credential also blocked), fast path + service-role key `200 {"ok":true,...}` (the live onboarding call, unaffected), no auth header `401`. `desk_tasks` confirmed unchanged by the verification itself (5 total, 0 created in window). The six batch-only task generators were removed from both the deployed function and the repo copy; they remain in git history.

**`daily-desk-cron` — the identity gap is still PARTIAL, deliberately not closed.** It is the one function with a live caller (`seedFounderPlaybook`, founder onboarding), which already derives identity via `requireUser` and verifies startup ownership before calling with the service-role key. Flipping `verify_jwt` closes the anonymous path while leaving that caller working — verified both ways live, including that the exact legitimate call shape still returns `200`. **The in-body gap remains open:** `founder_id`/`startup_id` are still caller-supplied query params with no in-function derivation, mitigated only by the *caller* checking ownership — the same "caller-checked, not function-enforced" pattern already found wrong elsewhere in this codebase. Any authenticated principal can still target another founder's ids. Full fix (`requireUser` + ownership check **inside** the function) is scoped for this function's rebuild — see the §7.1 open item. Not deferred indefinitely; not done under this pass.

**The standing lesson, beyond the individual fixes:** five of the six matching functions had **no caller anywhere** — no frontend, no cron, nothing. Two of those had their crons unscheduled during the §19 pass and were left deployed and open, which is the §7.1 trigger-vs-function distinction recurring for a third time. *No caller found is not the same as inaccessible.* An unreferenced deployed function is a live HTTP endpoint until it is made inert.

### 19d.2 Incident — an audit probe triggered the `daily-desk-cron` batch pass (11 Aug 2026)

Recorded because the mistake is more instructive than the fix, and because it is a production write that §4 requires confirmation for and that happened without it.

**What happened.** While testing which OpenAI-key-holding functions an untrusted caller could reach, an empty-body POST with an anon-key JWT was sent to `daily-desk-cron`. It returned `200` and **ran the full batch pass**: 4 founders processed, real OpenAI calls made, and **9 `desk_tasks` rows created across 5 real user accounts** (3 `fix_document`, 3 `profile_gap`, 3 `follow_up_watchlist`).

**Damage, verified rather than assumed.** `founder_documents`: zero rows modified, no `ai_feedback` written. `notifications` and `activity_log`: zero rows in the window, checked both before and after cleanup. Only trigger on `desk_tasks` is `desk_tasks_updated_at` (timestamp only, no side effects); only consumers are `desk-fn.ts` (read-for-display) and the cron itself. No email, no notification, no user-visible effect. Some OpenAI credit spent. The 9 rows were deleted by explicit id with `returning`, and the count re-verified afterward: 0 rows remaining in the window, `desk_tasks` back to 5 total — matching the figure recorded during Audit B.

**The reasoning error, which is the point of this entry.** §19c Audit B recorded the batch path as having *"no trigger of any kind — no `cron.job` entry, zero callers of the manual trigger."* That statement is true and was carried forward as though it meant the path was unreachable. It does not. **It means nothing invokes it *automatically*; a manual POST is itself a trigger.** This is the same trigger-vs-function conflation already recorded twice in §7.1 — made here by the same session that wrote those entries, one hour after flipping `verify_jwt: true` on this exact function, which is what made an anon-key JWT sufficient to reach it.

**Two compounding factors worth naming.** (1) Every other probe that day deliberately used inputs matching nothing — a nonexistent `deal_room_id` for `send-nudges`, a zero-UUID startup for `run-founder-coaching`. That discipline was not applied to a *parameterless* function, where "harmless input" does not exist and the only safe probe is not sending one. (2) The function's own `?founder_id=&startup_id=` fast path had been probed safely minutes earlier, which created false confidence that the endpoint was understood.

**Standing rule this produces:** *before probing any endpoint, establish what it does with the input you are about to send — including the empty input.* For a parameterless batch endpoint there is no safe probe; verify reachability by reading the deployed body and testing the auth gate only (`401` vs. anything else), never by executing it. **Never probe an unfamiliar endpoint with an empty body.**

**Disposition.** The batch pass was retired the same session (see below) rather than gated behind an admin secret — an unused manual capability attached to a function being narrowed is a liability, the same reasoning applied when deleting `triggerDeskCron`.

### 19d.1 BLOCKING REQUIREMENT — shared identity derivation — **CLOSED 12 Aug 2026**

The following has the same weight as the §4 confirm-first rule — it is a gate, not a recommendation:

> **No new Supabase Edge Function may be deployed without deriving caller identity through the shared identity-derivation helper.** `verify_jwt: true` alone does not satisfy this — the public anon key is a valid platform-signed JWT and passes it (§7.1). A function that reads a caller-supplied `user_id`, `founder_id`, `investor_id`, `startup_id`, or any other identity or ownership parameter from its request body or query string, without independently deriving the caller from their token and checking that the derived identity is entitled to the object named, is not deployable.
>
> This applies to functions with no known caller, functions intended only for cron, and functions described as internal or temporary. §19d's own inventory found five of six defective functions had no caller at all, and the highest-severity one was justified in its own comments as "scheduled infrastructure."

**The prerequisite is now built.** `supabase/functions/_shared/auth.ts` exports `resolveUid(req, supabaseUrl, supabaseServiceRoleKey)`, extracted from `ai-router`'s original implementation with no behavior change — same `/auth/v1/user` check, same anon-key rejection (GoTrue itself returns `403 bad_jwt: missing sub claim` before the function ever sees an id), same `string | null` return shape. Its file header states the §19d.1 rule directly, so it is visible at the point of use, not only in this file.

**All three functions that had independent inline implementations now import the shared module instead — verified with zero behavioral drift, not assumed:**

| Function | Before | After | Verified |
|---|---|---|---|
| `ai-router` | inline `resolveUid()`, raw `fetch` to `/auth/v1/user` | imports `resolveUid` from `_shared/auth.ts` | deployed v10; anon-key-as-bearer still `401 {"error":"Unauthorized"}`, identical to pre-migration |
| `extract-pitch-deck` | inline `supabase.auth.getUser(token)` | imports `resolveUid` from `_shared/auth.ts` | deployed v14; anon-key-as-bearer still `401 {"error":"Invalid token"}`, identical to pre-migration |
| `review-document` | inline `supabase.auth.getUser(token)` | imports `resolveUid` from `_shared/auth.ts` | deployed v8; anon-key-as-bearer still `401 {"error":"Invalid token"}`, identical to pre-migration |

Each function's full pre-existing adversarial matrix (no auth header, garbage token, anon key as bearer) was re-run post-migration and matched pre-migration responses exactly, including error message text — not just status code. `review-document` had no repo source before this (deployed-only, per the §7.5 "zero repo trace" pattern); it now has one, reconciled to the deployed body.

**Repo layout note:** the deploy tool resolves relative imports against each function's own directory, so a byte-identical copy of `_shared/auth.ts` lives inside `ai-router/`, `extract-pitch-deck/`, and `review-document/` alongside the canonical copy at `supabase/functions/_shared/auth.ts`. All four are confirmed identical by diff. Any future edit to the shared logic must be applied to all copies and re-verified identical — this is a known drift risk of the deploy mechanism, not a design choice.

**`daily-desk-cron` remains the one exception, tracked separately, not silently dropped.** It still derives no identity in-function (`founder_id`/`startup_id` are query params, mitigated only by the caller's own ownership check) — see the standing §7.1 entry. It was not migrated to the shared helper because it has nothing to migrate: adding real derivation there is the rebuild-scoped fix already on record, not a drop-in import.

## 19e. OpenAI API key leaked in the production client bundle — found and closed 11 Aug 2026

A live OpenAI API key shipped in plaintext in the production JavaScript bundle, publicly readable by anyone who loaded the site, for approximately eleven weeks. It is recorded as its own section rather than folded into §19d because the cause is unrelated: §19d is an authorization gap in edge functions, this is a build-configuration gap that exposed the credential itself. Closing every function in §19d would not have closed this, and did not.

### What was exposed

`https://hockystick.app/assets/index-CMdlIHN3.js` — the **main entry bundle, loaded on every page**, not a lazy route chunk — contained:

```
OPENAI_API_KEY:"sk-proj-PBpuySlVAi…"
```

Verified by fetching the deployed artifact and grepping it, not inferred from source. A local build from 19 Jul contained a **different** key (`sk-proj-jlTum…`) in the deal-room documents chunk. Both are compromised.

**Not exposed, checked explicitly:** `SUPABASE_SERVICE_ROLE_KEY` appears in the bundle only as a *variable reference* (`Ql("SUPABASE_SERVICE_ROLE_KEY")`, `t.SUPABASE_SERVICE_ROLE_KEY`), never as a value — it resolves server-side at runtime. No Resend key, no OpenRouter key. Exposure was limited to OpenAI.

### Timeline

| When | Event |
|---|---|
| 24 May, `6ae6dd6` | *"nodejs_compat for Cloudflare process.env, **OPENAI_ envPrefix**, AI key fallbacks."* Added `"OPENAI_"` to `vite.config.ts`'s `envPrefix` and `import.meta.env` fallbacks reading `VITE_OPENAI_API_KEY`. **This is the leak.** Vite inlines every var matching a listed prefix into client JS, so both `OPENAI_API_KEY` and `VITE_OPENAI_API_KEY` became client constants. It was solving a real problem — the key not resolving on Cloudflare — the wrong way. |
| 24 May, `f52e60e` | *"security: move all OpenAI calls server-side, **remove VITE_OPENAI from browser**."* **The remediation that missed.** It changed three source files (`DDWorkstation.tsx`, `ai-secure-fn.ts`, `app.deal-room.$id.tsx`) and never touched `envPrefix` or the env var. The code stopped *using* the key; the build kept *shipping* it. |
| between | The key was **rotated at some point and the rotation silently re-leaked** — the July local build and the August production bundle carry different keys. Rotation without fixing the mechanism reproduces the exposure with a fresh credential. |
| 11 Aug | Found during the OpenAI-key audit, at the step that greps the built artifact. Every function-side path had already been closed by then and none of it mattered: the key was readable directly. |
| 11 Aug, `c7fde04` | `"OPENAI_"` removed from `envPrefix`; both vars deleted from `.env.local`; `.dev.vars` added to `.gitignore` (it was **not** ignored, so recommending it for local secrets would have opened a new commit-the-secret path). |

### Why removing the line was safe

Checked before removing, not after: `patch-wrangler.mjs` sets `globalThis.__cf_env` from Cloudflare runtime secrets (lines 92, 494); `getEnvVar()` (`src/lib/env.ts`) reads `__cf_env` **first**, then `process.env`; and no current source reads the OpenAI key via `import.meta.env`. The problem `6ae6dd6` was solving is now solved properly, so the prefix was redundant, not load-bearing. `src/lib/env.ts` already carried a header comment stating *"Server-only secrets must NOT have VITE_ prefix. VITE_ vars are baked into the JS bundle and visible to anyone"* — **the rule was written down and the build config contradicted it.**

### Verification — on artifacts, at three stages

| Stage | Check | Result |
|---|---|---|
| Local rebuild | `sk-(proj-)?[A-Za-z0-9_-]{40,}` in `dist/client`, `dist/server` | 0 / 0 |
| Local rebuild | inlined env object | field gone entirely |
| **Deployed** entry bundle (`index-C60aSzai.js`) | key format, `OPENAI_API_KEY`, both key prefixes | 0 on every check |
| **Deployed** documents chunk (`app.deal-rooms._id.documents-CBIKJIX-.js`) — *the file that leaked it* | same four checks | 0 on every check |
| Deployed worker | key literal | 0; contains only the runtime lookup `globalThis.__cf_env||{}).OPENAI_API_KEY` |

Remaining `sk-` matches are Tailwind `mask-image-*` class names; remaining `OPENAI` matches are the worker's runtime `__cf_env` lookup, a privacy-policy sentence naming OpenAI as a subprocessor, and a bot-detection user-agent list. The new key is bound as an encrypted Cloudflare Pages secret (`wrangler pages secret list` confirms `OPENAI_API_KEY` present, `VITE_OPENAI_API_KEY` absent), set outside this session; its value was never handled here.

### THE STANDING RULE

> **A secret's exposure mechanism must be verified closed by checking the BUILT ARTIFACT, not by confirming the source no longer references it.**
>
> Source-level greps, removed call sites, and "we moved that server-side" commits prove nothing about what the bundler emits. Build tooling — `envPrefix`, `define`, `env` allowlists, framework-level public-var conventions — can inline a secret that no line of application code mentions. `f52e60e` did exactly the right thing at the source level and left a live key in production for eleven more weeks.
>
> **Whenever a secret is rotated, re-run the artifact check.** Rotation does not close an exposure mechanism; it refills it. That is precisely what happened here between May and August, silently.
>
> Concretely, after any change touching secrets, build config, or a key rotation: build, then grep `dist/` (client **and** server **and** worker) for the key's format — and where a deploy has happened, fetch the deployed bundle and grep that too. A local build and a CI build can differ in env, so the local check does not substitute for the deployed one. Both were run here and both are recorded above.

**Related, logged not actioned:** `OPENROUTER_API_KEY` remains bound as a Cloudflare secret though no function uses it any more (both OpenRouter fallbacks were removed 11 Aug — see §7.4). Unused bound secrets are worth pruning on their own pass. Separately, whether the exposed keys were actually used is only answerable from the OpenAI usage dashboard; that check is outside this repo and has not been done.

## 19f. Full 77-column `startups` row shipped to every anonymous visitor of a published profile — 70 days, closed 23 Aug 2026

Found incidentally, during the profile/founder migration group's step-0 content-trace audit (§20's next migration group), while tracing consumers of `startups`. Recorded as its own section, same weight as §19e, because the cause is a different class of defect from that one: §19e was a build-configuration gap that inlined a secret; this is a route-loader gap that inlined an entire private database row into public HTML. Neither incident would have closed the other.

### What was exposed

`p.$slug.tsx` — the public `/p/:slug` founder profile page — used the **service-role key** in its SSR `loader`, with `select("*")` against `startups` (77 columns), filtered only on `profile_published = true`. The page's own section-visibility gating (`getVisibility`/`SectionGate`) decided what to *render*; it never touched what was *queried*, so the whole row was serialized into the SSR payload regardless of gating. Verified live against `https://lengdon.com/p/atlas-robotics`, a real published profile whose own `section_visibility` marks `financials` as `deal_room`-only:

```
founder_email:"optimus@atlas.com"
burn_rate:"200000",runway_months:14,unit_economics:"65%"
org_code:"000001"
completeness_score:100
```

`founder_email` and `pitch_deck_url` were exposed unconditionally on **every** published profile regardless of section visibility — neither field is rendered under any `SectionGate` on the page at all, so they were never displayable, at any access level, to anyone. `select(*)` does not know that; it shipped them anyway.

**Verification false-negative, worth recording precisely because it nearly produced a wrong all-clear.** The first check of the production response reported **zero occurrences of everything** — `founder_email`, `burn_rate`, all of it. The response has no newlines and contains a byte sequence that makes plain `grep` treat the file as binary, which silently suppresses matches rather than erroring. Only re-running with `grep -a` (force text) surfaced the leak. This is the same class of lesson as §6's "claims are not evidence," extended: a clean grep result is not evidence unless the file was confirmed to have been read as text first. Applied as the standard for the fix's own verification below.

### Root cause

`startups` has no anon SELECT RLS policy at all — `startups_own` requires `founder_id = auth.uid()`, so an anonymous visitor sees zero rows. The service-role client was added to work around this and make the public profile route actually return data, and the projection was never narrowed to match. Same shape as §19e's root cause in spirit — a real problem (the route was broken for logged-out visitors) solved by escalating privilege rather than by narrowing what was asked for.

**The correct pattern already existed in this codebase, one file over.** `/i/:slug` (the investor mirror of this exact feature) uses the anon client calling `get_public_investor_profile()`, a `SECURITY DEFINER` SQL function that re-checks `profile_published` and returns only that row's own `public_fields` whitelist — enforced in SQL, not in JSX. Its own source comment states the principle directly: *"enforced in SQL, not just by this page's JSX."* The founder side never got the equivalent. This is the §7.5 "check the founder/investor mirror side even when only one side was flagged" lesson, recurring — the mirror side wasn't flagged by anything, it was found by tracing consumers of a table during an unrelated audit.

### The fix

`supabase/migrations/20260823000000_public_founder_profile_whitelist.sql` — `get_public_founder_profile(p_slug)`, `SECURITY DEFINER`, `search_path = public, pg_temp` (pg_temp last, per §7.2). Re-checks `profile_published = true` internally. Returns:
- An **always-public** field set (19 fields — identity header content: `company_name`, `tagline`, `founder_name`, `why_now`, etc. — plus `founder_id`, needed for the page's own owner-preview check).
- Five **conditional** field groups (`business_model`, `market`, `traction`, `financials`, `team`), each returned only when that row's own `section_visibility[section] = 'public'`.

The authenticated owner-preview path (client-side, `startups_own` RLS, `select("*")` gated on `founder_id = auth.uid()`) was confirmed correct and left untouched — it never had this defect, since RLS was already doing real work there.

### THE STANDING LESSON

> **"Zero readers" is a claim about the code, not about what a `service-role` `select(*)` actually transmits — the two are not the same fact.** The original step-0 audit of this table correctly reported that three cap-table columns (`founder_ownership_pct`, `has_options_pool`, `total_shareholders`) had no reader anywhere in the codebase, and that was true. But "no reader" only describes what the *client code chooses to display* — it says nothing about what a wide `select(*)` call *sends over the wire*. `founder_email` and `pitch_deck_url` are the sharper version of the same fact: they had **zero readers under any condition**, on a page that had been serving them to the public internet for ten weeks. Treating column exposure as safe because nothing currently renders it is the exact reasoning error that let this ship — visibility must be enforced by what is queried, not by what is rendered, and a column with no reader is not evidence of a column with no exposure.

1. **Content-trace audit before trusting any file/table grouping** — a table or file can look like it belongs to one feature by name and still be dual-role or misclassified; verify by reading actual usage, not by import graph or naming alone (this is the general form of the lesson CLAUDE.md §7.5 already records).

5. **Empty states and error semantics, as their own step** — see §20.4. Not folded into the client rewire and not left to the presentation pass; specced and built between the two.
6. **DESIGN v2 presentation rebuild, as its own reviewable step** — do not fold presentation into the data-layer rewire step; keep it a separate, explicitly-reviewed pass over already-proven primitives, as done for the documents group.
7. **Push only after all of the above is reviewed as one unit, against the §20.3 exit checklist** — the documents-group precedent: six commits, one push, after every stage was individually approved.

### 20.4 Empty states and error semantics as explicit steps

These are step 5 in the §20.1 sequence, between the client rewire (step 4) and the DESIGN v2 presentation rebuild (step 6). Not polish, not foldable into either neighboring step — they are the difference between a product that reads as six months old and one that reads as five years old.

**Empty states.** One per surface in the group. Each names what would appear and the one next action available from that empty state. No illustrations. Per DESIGN.md §7.3.

**Error semantics.** Each failure class in a group needs its own defined behaviour — retryable, not retryable, partially applied, or unknown — because each reads differently to the user and silently defaulting to one generic error message is itself a defect. Define behaviour explicitly for at least:

- Write failure after a user action
- Session expiry mid-action
- Concurrent edit conflict
- Third-party provider failure
- Upload interruption

**No optimistic UI on consequential actions.** A consequential action (anything Commit-class per Foundation Document §15.2 / CLAUDE.md §8.2) shows a pending state until the record confirms — never an optimistic success state that could be rolled back under the user.

### 20.9 Duplicated surfaces and dead controls — removed 13 Aug 2026

### 20.11 The action-layer split failure — an eleven-day production outage of the entire gateway

**Found 13 Aug 2026, root-caused and fixed 13–16 Aug 2026.** `defineAction`, the sole sanctioned chokepoint for every client→`pack_v1` read and write (§8.1, §13.2/§3.7), silently ran its entire server-side handler **in the browser** for every action in both migrated groups, for eleven days, in production. This section is written at the same weight as §19e — a live security- and correctness-relevant production defect, found the hard way, root-caused against the built artifact rather than reasoned about.

**Root cause.** `defineAction(def)` **returned** `createServerFn(...)`. TanStack Start's server-fn transform is a compile-time AST rewrite that only recognizes a **statically-analysable, top-level** `createServerFn(...).handler(...)` call — it walks the source looking for that literal shape and rewrites it into a client-side RPC stub plus a server-side registration. A `createServerFn` call returned from inside a function body is invisible to that walk: no RPC stub is emitted, no server registration happens, and the entire handler — `requireUser`, the `service_role` Supabase client, the `pack_api` RPC call, the `append_record` write — is bundled into the **client** JavaScript and executed **in the browser**. There, `getEnvVar("SUPABASE_SERVICE_ROLE_KEY")` correctly returns empty (the secret is never shipped to the client — see the security note below), so `requireUser` returned `{ok:false, error:"db_unavailable"}` on every single call, having made **zero network requests**. Two call sites handled that thrown/returned failure differently, both wrong in different ways: list-view queries (`app.deal-rooms.index.tsx`, `useRaiseProgress`, `useDealFlowProgress`) caught it and degraded to `[]`, rendering a plausible-looking "no deal rooms" state to founders who had real rooms; detail routes (`useDealRoomContext`) let it propagate into `roomError`/`accessError` and failed closed, showing "Couldn't verify your access" to genuine members of their own deal rooms.

Proven against the built artifact, not inferred: two server functions declared the two ways, built through the real pipeline. Plain top-level `createServerFn` → **0 hits** in `dist/client` (correctly stripped, replaced by an RPC stub keyed on a 64-hex function id). Factory-wrapped (the `defineAction` shape) → **1 hit** in `dist/client` — the full handler body, visible in the minified bundle sitting directly next to the plain version's stub for comparison.

**Blast radius: every `callAction` site in both migrated groups**, i.e. everything routed through the action layer as of 13 Aug 2026:
- **Documents group** (landed 4–5 Aug): `pack.get`, `documents.requestAccess`, `documents.grantRelease`, `documentRender`, and the seven deal-room-documents actions (`docListRoom`, `docListLibrary`, `docListInvestor`, `docInsert`, `docUpdate`, `docViewInsert`, plus the four `docRequest*` actions).
- **deal-room-core group** (landed 9–10 Aug): all eleven actions — `roomGetIdentity`, `roomGetWorkflowState`, `roomGetDealTerms`, `roomGetMedia`, `roomGetTermSheet`, `roomListByStartup`, `roomListProgressFounder`, `roomListProgressInvestor`, `roomUpdateDealTerms`, `roomAppendProductImage`.

Every deal-room detail route, both founder and investor room lists, deal terms, workflow state, media, investor memo, term sheets, and the entire documents tab — 25 actions across every surface the deal-room-core DESIGN v2 rebuild (the pass immediately preceding this one) had just finished re-verifying.

**Duration: 11.24 days (269.8 hours), pinned from Cloudflare's own deployment history, not inferred from commit dates** — per the standing discipline this file already applies to cron logs and deployed-function inventories (§7.5, §19). The Cloudflare Pages CLI caps `deployment list` at 25 rows; the full history was pulled via the account's own OAuth token (found in `~/Library/Preferences/.wrangler/config/default.toml`) against `GET /accounts/{id}/pages/projects/vcroom-main/deployments`, which paginates correctly and reported `total_count: 633`.
- **First bad deployment: `c64e9cf`, 2026-08-05T06:35:49Z** (deployment id `28a95bcd-a283-4c60-8d22-c55abe56c19a`). The commit that introduced the vulnerable shape, `e50c04e` (4 Aug 17:07), had no deployment of its own — no commit between it and `b186d5a` (4 Aug 21:26, the commit that first wired a live route, the documents tab, to call the broken action unconditionally on mount) shows an individual Pages deployment. `c64e9cf` is the first deployment timestamped after `b186d5a` and is confirmed as the bundling point where a real, unguarded route first called a `defineAction`-derived function in production.
- **Fix deployment: `52f8412`, 2026-08-16T12:21:43Z** (deployment id `586b92f0-6a08-4d7b-8592-000b32759e26`).
- 633 total deployments exist in this project's history; only the ~30 in the relevant window were inspected. No gap in that window was left unresolved by inference — every commit between the two boundary deployments was individually checked against `git log` for whether it touched a live route's call site.

**Why this survived every review gate in both migrated groups.** Every authorization verification in both groups — the adversarial matrices in deal-room-core's step 2a/2b/2c, the documents group's own sign-off, everything §20.3's exit checklist required — was run by calling `pack_api` functions **directly**, as `service_role`, via `execute_sql` or an equivalent server-side path. That proves, correctly, that the database schema and the `authz_*` primitives are right. It proves **nothing** about whether a browser can reach them at all, because it never went through the actual client→`createServerFn`→worker→handler path a real user's browser uses. No SQL-level check — however adversarially thorough — could ever have caught a transport/bundling failure, because the failure happened entirely on the client side, before any SQL was ever issued. §20.3 now requires a transport-level check (a real browser call returning real data) as its own line, separate from and not satisfied by the authorization check, for exactly this reason.

**How it was found and root-caused — four wrong findings first, and the lesson from each.** This was investigated across several sessions with the user directing an increasingly disciplined trace; the record is kept because the wrong turns are as instructive as the right one:
1. First reported as a **path mismatch** (`500`/`307`/`404` across different guessed `_serverFn` paths) — wrong. The path was always correct; the probes were missing `Origin`/`Referer` (tripping the framework's CSRF check) and the `x-tsr-serverFn: true` marker header.
2. Then reported as **`Seroval Error (step: 3)`**, a deserialization failure in the transport itself — wrong. That error appeared only in response to hand-constructed `curl` payloads that were never valid seroval wire format to begin with; it never appeared in real client traffic.
3. Then reported as **the transport being broken app-wide** — an overcorrection built on finding #2.
4. Then reported as **"production differs from local"** (local showed `db_unavailable`, production showed nothing) — wrong. The production capture used `page.on("console")` without serialising the log arguments; the error was there, unread.

**The lesson, stated plainly because it is the one worth keeping: probing a system with hand-constructed requests tests your understanding of the protocol, not the system.** Every wrong finding above came from constructing a request by hand and reasoning about the response. The one finding that held up — the actual root cause — came from capturing **genuine client traffic** (via Playwright's `page.on("console")` with proper argument serialization, then a full CDP `Network.*` session, then a wrapped `console.error` capturing a real stack trace pointing at the exact `queryFn` line in the deployed bundle) and reading what the real client actually sent and received. When the two disagree, trust the captured traffic, not the hand-built probe — no exceptions, and re-verify anything reasoned about a system's behavior from a probe you constructed yourself before treating it as a finding.

**Security note — the guarantee was correct in the type system and unreachable at runtime; it failed safe by accident, not by design.** §13.2/§3.7's "no action may skip authorization" guarantee was real: `ActionDef` requires `authorize` as a non-optional field, so no action anywhere failed to declare one. But because the handler ran in the browser, `authorize` and every downstream authorization check never mattered — the request never reached a point where the database's real RLS/`authz_*` primitives could be consulted, because `requireUser` failed first, on the missing service-role key, before authorization was ever evaluated. **The system failed closed here specifically because the service-role key is correctly never shipped to the client** — checked explicitly during the investigation: the key literal is absent from every client bundle, no `service_role` JWT payload appears anywhere client-side, and only the environment-variable *name* (`SUPABASE_SERVICE_ROLE_KEY`) appears, inside `getEnvVar`'s lookup-chain source. Had that key been present client-side for any other reason (see §19e — it was, once, for a different secret, for eleven weeks), this exact bug would not have failed closed: it would have executed the full handler, including `authorize` and the real database call, entirely client-side, with the service-role client available to an attacker's browser session. **The design was correct. The build silently did not honor it. Those are different failures, and the second one very nearly hid the first one being untested by making everything fail loud enough to notice — but for eleven days, `[]`-on-failure fallbacks (§7.4) made sure most of it didn't.**

**The fix, verified against the built artifact and in production (52f8412, e7c4ea1):**
- `defineAction` → `runAction(def, data)`, a plain async function holding the identical 7-step pipeline moved verbatim. All 25 actions now bind their own top-level `createServerFn`; factories build the `ActionDef` object only, never a server function.
- The chokepoint guarantee is preserved **structurally**: `ActionDef` still requires `authorize`+`record` (won't type-check otherwise); `serviceClient` is unexported, so a service-role handle is obtainable only inside `runAction`.
- **Both enforcement mechanisms**, not either/or, per the explicit instruction that produced them: an eslint rule (`src/lib/actions/**`) catching the wrong *shape* at author time, and `scripts/check-action-split.mjs` — wired into `postbuild`, failing the build in **both directions** (every action routes through `runAction`; zero `pack_api` handler bodies reach `dist/client`) — catching a wrong *artifact* for any reason, including causes nobody anticipated, which is what this bug actually was. Negative-tested: reintroducing the factory shape fails the build with the exact diagnostic. Has a stale-`dist` guard after an early version of the check reported on pre-fix output.
- Verified: build gate green (25 actions, 18 RPCs server-only, 0 client-side); deployed-artifact scan (0 handler bodies across all entry-linked chunks); full blast-radius check, both roles, all 14 route combinations, production, real fixture data (`denied=false`, `db_unavailable=false`, `200 {"ok":true,...}` everywhere) — including the founder room list rendering **"2 rooms"** with real investor names and reference numbers, the first real gateway data served since 5 Aug.
- The `[]`-on-failure fallbacks that hid this for eleven days were separately reverted the same day (§7.4) — verified by forcing a real failure and confirming the UI now shows "Deal rooms could not load" with a retry, not a fake empty state.
